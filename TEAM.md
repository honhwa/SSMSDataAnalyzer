## What this round taught, beyond M1

**Green tests proved nothing about SSMS.** Query History shipped four times — 0.19.0 through
0.19.3 — without recording a single query, while 353 unit tests passed throughout. Two causes,
both invisible to the test suite:

1. The in-memory file-system fake treated paths as opaque strings, so nothing noticed that no
   code created the history folder. **A test double must fail wherever the real dependency
   would.** The fake now throws like Windows, and file-touching logic is backed by a real-disk
   test.
2. Options were read on a background thread, where `GetDialogPage` throws `COMException`. **Never
   touch a shell service off the UI thread; snapshot on the UI thread and pass the value in.**

**A silent feature needs a visible reason.** What actually ended the guessing was making the
window explain itself — "5 executions seen, 5 queued, 0 written, history file could not be
opened (COMException)". Two rounds of speculation became two exact diagnoses. Diagnostics that
count "accepted" as "done" are worse than none: the first version reported success for work that
never reached the disk.

**Agents build what compiles; the lead owns what is true.** Every delegated wave needed a lead
fix that a build could not catch — a trim that would duplicate entries after an interrupted run,
a Copy that ignored multi-select, a report whose "evidence" was compile errors rather than
behaviour. The pattern is not that agents are unreliable, it is that *compiles* and *correct* are
different claims, and only one of them is self-checking.

**Verify against the real thing when the real thing is reachable.** The star-expansion work was
checked with a harness running the actual ScriptDom parser, and the icon IDs were read out of
SSMS's own image catalog by reflection rather than copied from documentation. Both took minutes
and both would have shipped broken otherwise — the previous icon declaration was self-
contradictory and had been drawing nothing since M3.

## Why this partition

Directory ownership is **exclusive and disjoint** — two agents writing the same file would
silently clobber each other. *(Written when this was not yet a git repo, so there was no merge
machinery to fall back on. It is one now, and the rule has been kept anyway: parallel agents in
one working tree still overwrite each other, and disjoint lanes are what make their output
reviewable one piece at a time.)* Every agent was told: never touch a path outside your own, report cross-area
needs to the lead instead.

The shared model types were frozen in `CONTRACT.md` **before** any agent started, so four
parallel streams converge on one set of shapes. Agents B and D are deliberately coding against
types that Agent A is writing concurrently — they were told Core may not compile yet and to
proceed anyway. That is the whole point of freezing the contract first.

### Amendments issued this round

1. `ColumnProfile.TotalRowsContext` made public — an internal value made hand-built profiles
   report `Flags = None`, turning flag-derivation unit tests into false passes.
2. Flags suppressed entirely on empty tables — at 0 rows `Dead` degenerates into restating the
   row count rather than reporting a finding about a column.
3. Numeric literals permitted where T-SQL rejects parameters (`TABLESAMPLE`, `MAX_GRANT_PERCENT`,

4. `AggregateSupport.NoDistinct` implies `NoMinMax`; type matrix adopted from A's empirical
   testing against the live instance.
5. VSIX packaging requires the explicit `Microsoft.VsSDK.targets` import.

### Amendment 6 — the spike overturned a plan assumption

PLAN.md specified late-bound reflection for Tier A as insurance against an unsupported API that
might not exist in the VS 18 shell. Agent C proved the assumption wrong in the useful direction:
the API exists and **every type on the path is public**. Compile-time references replace
reflection.

The spike also caught a trap that would have cost days: **the OE node context menu is a WinForms

compiles fine, installs fine, and silently never appears. `.vsct` is now removed from the Tier A

## What the parallel structure actually bought

Nearly every defect found was at a **seam** — no single agent could have seen it:

- The VSIX shipped `Microsoft.Data.SqlClient` **5.2.2** into a host already running **6.1.5**,
  with the native SNI library missing entirely. Found by unzipping B's artifact and comparing it
  against the SSMS install. The package built clean and would have failed on first click.
- Bumping Core to 6.1.5 (A) pulled a *different* transitive set, leaking eight more assemblies
  into B's payload. Had those two changes landed in the other order, the exclusion list would
  have been silently incomplete.
- D's test project pinned the SqlClient version independently of Core, so A's bump turned the
  suite red with `NU1605`.
- A pass-1 timeout discarded the whole profile while the distinct pass degraded gracefully —
  an inconsistency visible only by comparing the two passes side by side.

## Corrections that went the other way

The lead was wrong twice, and both were caught by agents doing the right thing:

1. **Amendment 5** — I recorded B's "the VS workload isn't needed" conclusion as fact. True in
   substance, wrong in mechanism, and the mechanism was the blocker: the auto-imported targets
   file is 18 lines of environment variables, and the real packaging targets need an explicit
   import.
2. **Amendment 11** — I asserted trailing-space distinct behaviour diverges under `_BIN2`. It
   does not; that is ANSI padding, not collation. **Agent D tested the hypothesis instead of
   seeding against it, and reported the discrepancy rather than fabricating data to match the
   contract.** Agent A reached the same correction independently; the lead reproduced it a third
   time.

The second is the one worth keeping: a plausible claim from the lead entered a binding contract
untested and would have produced a test asserting a divergence that does not exist.
**Test the hypothesis before it becomes a requirement.**

## The discipline that found the real bugs

Every significant catch came from the same habit — *run it, don't derive it*:

- D got **251** distinct, not the obvious 252, by executing the query.
- D proved the banned-token guard worked by narrowing it until it caught its own test files.
- B proved the payload guard worked by disabling suppression and watching the build fail on 42 files.
- A proved collation safety by first producing `Msg 468` **on demand** from a negative control —
  because "no error" means nothing unless the test could have produced one.

## Still not proven — *as of M1; superseded, see below*

**The extension has never run inside SSMS.** Everything verified is build-time or CLI-level:
the engine is thoroughly proven, the VSIX is proven only to build and package correctly.
Loading it into SSMS 22 is the next milestone and the next place defects will surface.

> **This was right, and it is where nearly every defect since has come from.** The extension has
> run in SSMS since M3 and every feature in the table at the top has been exercised there. The
> prediction held: the build has been green for defects that made features completely
> non-functional — an icon that drew nothing, a history that recorded nothing, a `SELECT *` that
> declined every grid. The standing rule that came out of it: **build and send a fresh `.vsix`
> before asking the user to check anything**, and never describe SSMS behaviour as verified when
> only the build was.
